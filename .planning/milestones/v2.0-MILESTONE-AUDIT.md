## Integration Findings

### GAP-1: Runtime relay activation config is dropped

Status: blocking.

Affected requirements: ACT-01, ACT-02, REL-01, REL-02, REL-03, OBS-01,
OBS-02, OBS-03, OBS-04, BOUND-03, BOUND-04.

`RuntimeConfig.relay` is resolved in
`packages/open-bitcoin-rpc/src/config/loader.rs`, but
`ManagedRpcContext::from_runtime_config_with_store` constructs the managed
network with `ManagedPeerNetwork::new`. That constructor delegates to
`new_with_relay_activation(..., RelayActivationConfig::default(), false)`, so
daemon/runtime contexts ignore explicit relay activation settings and remain
default-off for serving/fanout eligibility.

Evidence:

- `packages/open-bitcoin-rpc/src/config/loader.rs:147`
- `packages/open-bitcoin-rpc/src/context/network.rs:93`
- `packages/open-bitcoin-node/src/network/relay_serving.rs:222`
- `packages/open-bitcoin-node/src/network/relay_serving.rs:233`

### GAP-2: Transaction download scheduling does not consume relay eligibility

Status: blocking.

Affected requirements: ACT-02, INV-02, INV-03, DL-01, DL-02.

`TxAnnouncementInput` contains peer identity mode, local facts, preferred-peer
state, and overloaded-peer state, but it does not carry a
`RelayEligibilityDecision` or activation gate. The scheduler can therefore
schedule transaction downloads from peers without the Phase 100 relay
eligibility decision participating in the Phase 101 download path.

Evidence:

- `packages/open-bitcoin-network/src/peer/transaction_relay/scheduler.rs:32`
- `packages/open-bitcoin-network/src/peer/transaction_relay/scheduler.rs:88`
- `packages/open-bitcoin-node/src/network/relay_serving.rs:292`

### GAP-3: Durable mempool recovery does not repopulate relay serving/fanout state

Status: gap.

Affected requirements: MEM-06, REL-01, REL-02, OBS-01, OBS-02, OBS-03,
OBS-04.

Durable mempool recovery replays snapshot records directly into a bare
`Mempool` through `MempoolSnapshot::replay_into_mempool`. Live accepted
transactions update the managed transaction indexes and relay serving cache
through `ManagedPeerNetwork::store_transaction`, and fanout evidence is
projected from managed relay state. Recovered transactions therefore do not
repopulate serving/fanout state in the same way as live accepted transactions.

Evidence:

- `packages/open-bitcoin-node/src/storage/mempool_snapshot.rs:74`
- `packages/open-bitcoin-node/src/network/inventory.rs:67`
- `packages/open-bitcoin-node/src/network/relay_fanout.rs:300`
- `packages/open-bitcoin-node/src/network/relay_fanout.rs:321`

## Release Boundary

v2.0 remains bounded to transaction relay and mempool participation evidence. It
does not claim compact block relay, bloom/filter serving, broad package relay,
public transaction relay by default, public-network relay CI, production
full-node readiness, production service operation, or production-funds wallet
safety.
