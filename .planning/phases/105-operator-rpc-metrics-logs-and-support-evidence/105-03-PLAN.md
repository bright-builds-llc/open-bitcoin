# Phase 105 Plan 03: Support Redaction

<objective>
Sanitize Phase 105 relay and mempool evidence for support bundles before docs, parity records, and closeout verification make that evidence durable.
</objective>

<context>
Plans 105-01 and 105-02 make relay evidence visible. This plan makes that visibility safe to collect in support bundles. The support bundle is the highest-risk surface because it intentionally aggregates operator data, so redaction must be stricter than ordinary display rendering.
</context>

<action>
Extend support bundle rendering to include a concise relay and mempool evidence section sourced from the shared Phase 105 status contract. Extend redaction so support output rejects or redacts:

- raw transaction hex
- txid-like and wtxid-like 64-hex identifiers unless explicitly allowlisted by existing support rules
- socket-address shapes, peer endpoints, host:port values, and endpoint markers
- peer identifiers
- permission strings
- credentials, tokens, cookies, secrets, and authorization values
- suspicious hex values in relay evidence
- dynamic metric labels and free-form relay labels

Prefer deny-by-default redaction for relay evidence. If an existing support redaction allowlist conflicts with Phase 105, add a narrower relay-specific rule instead of weakening global redaction.

Ensure support JSON and Markdown use the same sanitized relay and mempool projection through `support_status_for_bundle` or a closely related helper. Do not let Markdown rehydrate unredacted status independently.

Add the UI-SPEC support next-action guidance in Markdown: bounded local status only and local troubleshooting/parity-review evidence only; not public propagation, compact-block relay, a release validator, public-network proof, production-service proof, production full-node readiness proof, or production-funds wallet safety proof.
</action>
