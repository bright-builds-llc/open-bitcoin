<interfaces>
RPC names and results:

- `listprunelocks` params `[]`. Result: JSON array of `{ "name", "height_first", "height_last" }`.
- `setprunelock` params `["name", height_first, height_last]`. Same name replaces. Result is that object. Refuse empty name, `height_last < height_first`, and `height_last > u32::MAX - 10` with `RpcErrorCode::InvalidParameter` before any write.
- `clearprunelock` params `["name"]`. Missing name returns `{ "success": false }` and does not write. Present name returns `{ "success": false }` only when absent; success is `{ "success": true }`. No `"*"` and no null-height delete on `setprunelock`.
- `pruneblockchain` params `[height_or_timestamp: i64]`. Result is a JSON number. `0` returns `0` immediately and does not call `plan_manual_prune`. Negative is `RpcErrorCode::InvalidParameter` message `Negative block height.`. Disabled is `RpcErrorCode::MiscError` message `Cannot prune blocks because node is not in prune mode.`. Chain too short is `MiscError` message `Blockchain is too short for pruning.`. Target above tip is `InvalidParameter` message `Blockchain is shorter than the attempted prune height.`. Keep window is `InvalidParameter` message `target is inside the 288-block keep window`. Timestamp miss is `InvalidParameter` message `block at the requested timestamp was not found`.

`MethodOrigin::BaselineParity` for `pruneblockchain`, `listprunelocks`, and `setprunelock`. `clearprunelock` is `MethodOrigin::OpenBitcoinExtension`. All four are `MethodScope::Node`.

CLI, exact spellings:

```text
open-bitcoin prune run <height-or-timestamp>
open-bitcoin prune lock list
open-bitcoin prune lock set --name <name> --height-first <n> --height-last <n>
open-bitcoin prune lock clear --name <name>
```

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| RPC client → pruneblockchain | Untrusted height or timestamp can ask for a delete. |
| RPC client → setprunelock | Untrusted name and heights become durable locks. |
| CLI → RPC | The CLI must not become a second writer against the open database. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-150-01 | Spoofing | success height | mitigate | The return is `get_prune_height` after flush, or `-1`. It is not `pruned_count` and not the plus-one info field. Disabled tests assert `load_have_pruned` stays false. |
| T-150-02 | Tampering | disabled or keep-window prune | mitigate | Those branches return before `flush_applying_prune_plan`. The keep-window message says refused and the test asserts the payload remains. There is no clamp to `tip - 288`. |
| T-150-03 | Tampering | locks ignored by the manual plan | mitigate | `plan_manual_prune` and the flush both receive `load_prune_locks()`. Plan 03 already feeds that record to resume. |
| T-150-04 | Information disclosure | CLI and RPC lock JSON | mitigate | Lock JSON is name and two heights for list/set. Support evidence is Plan 06 and must not reuse this JSON. Error strings in this plan do not include the datadir. |
| T-150-05 | Tampering | mode bypass | mitigate | Disabled is checked by `plan_manual_prune` from the mode Plan 02 stored. The RPC does not accept a mode argument. |
| T-150-06 | Tampering | lock name as a path | mitigate | `setprunelock` writes through `sync_prune_locks` only. The name is not concatenated with the datadir, and an empty name is `InvalidParameter`. |
</threat_model>
