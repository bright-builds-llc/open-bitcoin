<threat_model>
## Trust Boundaries

| Boundary | Description |
| --- | --- |
| peer transaction to orphanage | Untrusted peer transactions become bounded in-memory candidates after mempool reports missing parents. |
| orphanage to scheduler | Parent request candidates cross into Phase 101 scheduler state as typed `TxRelayId` requests. |
| peer disconnect to cleanup | Peer-owned orphan and transaction request state must be removed without stale fallback state. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
| --- | --- | --- | --- | --- |
| T-102-02-01 | Denial of Service | `TxOrphanage` | mitigate | Enforce total cap 100, per-peer cap 25, injected-time expiry, deterministic eviction, and max 32 reconsiderations per parent. |
| T-102-02-02 | Denial of Service | orphan parent requests | mitigate | Route parent fetches through `TxDownloadScheduler::request_parent` so in-flight and announcement caps still apply. |
| T-102-02-03 | Information Disclosure | orphan evidence labels | mitigate | Use only fixed labels `orphaned`, `parent_requested`, `orphan_evicted`, `orphan_expired`, and `orphan_reconsidered`; do not expose raw transaction hex, txids/wtxids, endpoints, permissions, or credentials in label strings. |
| T-102-02-04 | Tampering | reconsideration state | mitigate | Avoid recursive walks; return bounded candidates and require shell code to record accepted/rejected/still-missing outcomes explicitly. |
| T-102-02-05 | Elevation of Privilege | direct peer/socket mutation of mempool state | mitigate | Keep orphanage in `open-bitcoin-network` pure; it returns actions only and cannot call mempool APIs or socket writers. |
</threat_model>
