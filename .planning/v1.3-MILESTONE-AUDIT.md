## Blocking Gaps

### G-01: Live-smoke progress detection is not wired to fresh daemon sync status

**Severity:** blocking

**Affected requirements:** PROOF-03, PROOF-04, PROOF-05, OBS-02, SEC-03

**Evidence:**

- `scripts/run-live-mainnet-smoke.ts` builds the status command as
  `open-bitcoin-cli getblockchaininfo` during the daemon run.
- `readSyncStatus` parses that RPC response and hardcodes
  `outboundPeers: 0` and `phase: "rpc_getblockchaininfo"`.
- The pass condition uses `headerDelta` and `blockDelta` from those snapshots.
- `getblockchaininfo` uses `context.maybe_durable_sync_state()` when available,
  but that state is loaded into `ManagedRpcContext` at startup and returned from
  a stored field.
- The fresh sync-control status path exists as `open_bitcoin_sync_status`, but
  the live-smoke runner does not poll it.
- Phase 50 UAT shows the mismatch directly: selected report snapshots have
  `lifecycle=synced` and `phase=rpc_getblockchaininfo`, while final durable
  status has `lifecycle=active` and `phase=steady_state`.

**Impact:**

A successful public-mainnet header or block progress run could be missed or
misclassified. The diagnosed-blocker packet contains useful endpoint outcomes,
typed no-progress cause, final durable status, and next operator action, but the
snapshot loop is not anchored to the fresh daemon sync truth surface. That means
the milestone cannot claim the Phase 50 closeout path is fully integrated.

**Close criteria:**

- Live-smoke polling reads fresh Open Bitcoin daemon sync-control status, or
  `getblockchaininfo` refreshes durable sync state per request before reporting.
- Snapshot `lifecycle`, `phase`, outbound peer count, latest error, and progress
  heights are consistent with final durable daemon status for both progress and
  diagnosed-blocker outcomes.
- Deterministic tests prove the live-smoke runner detects progress and no
  progress through the same fresh status source.
- Phase 50 UAT is regenerated or amended with fresh-status evidence.

## Non-Blocking Debt

### D-01: Support bundle live-smoke summary misses nested schema fields

**Affected requirement:** OBS-03

The support bundle links to live-smoke artifacts, but the summary allowlist
checks only top-level keys. Current schema v2 reports keep useful fields under
nested `result`, so generated support evidence can report
`summary_fields_unavailable` even when the source report contains status,
typed cause, and next-action data.

**Follow-up:** Teach support evidence ingestion to summarize schema v2 nested
`result` and artifact paths without exposing raw logs or credentials.

### D-02: `open-bitcoind` preflight message is stale

**Affected requirement:** OBS-02

`open-bitcoind` starts the daemon sync worker and `TcpPeerTransport`, but its
preflight stderr still says peer transport and unattended IBD are not started by
this phase. This does not block deterministic behavior, but it weakens operator
truth surfaces.

**Follow-up:** Refresh the message to describe the current opt-in worker and
the remaining non-claims without contradicting runtime behavior.

### D-03: Phase 44 optional public-network UAT remains skipped

**Affected requirement:** PEER-03

`gsd-tools audit-uat --raw` reports one unresolved skipped UAT item:
Phase 44 test 4, "Live Smoke Report Shows Contribution Evidence." The skip is
documented as a real-network `handshake_failure`; deterministic fixture evidence
passed locally. This is not a standalone milestone blocker, but it should remain
visible because it touches the same live-smoke evidence path as G-01.
