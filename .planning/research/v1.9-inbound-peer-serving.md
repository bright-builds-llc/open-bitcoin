# v1.9 Research: Inbound Peer Serving and Network Participation Boundary

**Date:** 2026-06-25
**Scope:** Local source scan for planning v1.9 requirements and roadmap. This note supplements, rather than refreshes, older project-level research files in `.planning/research/`.

## Question

What should the next milestone build so Open Bitcoin can become a better network participant without accidentally claiming relay or production readiness?

## Current Open Bitcoin Anchors

- `packages/open-bitcoin-network/src/peer.rs` already has a pure `PeerManager`, `ConnectionRole::{Inbound, Outbound}`, `add_inbound_peer`, handshake state, inventory serving actions, transaction/block receive actions, and per-peer block in-flight limits.
- `packages/open-bitcoin-node/src/network.rs` wraps the pure peer manager in `ManagedPeerNetwork`, tracks inbound/outbound counts, serves known inventory, submits received transactions to the local mempool, and connects received blocks.
- `packages/open-bitcoin-node/src/sync.rs` and `packages/open-bitcoin-node/src/sync/tcp.rs` are outbound-sync-oriented shell code: they connect to peers, send/receive wire messages, enforce payload `MAX_SIZE`, and persist sync evidence.
- `packages/open-bitcoin-rpc/src/config/open_bitcoin.rs` has a `sync` config block but no inbound listener, peer permission, ban, or address-management config surface yet.

## Knots Baseline Anchors

- `packages/bitcoin-knots/src/net.cpp` covers listener/bind behavior, local address advertising, connection management, inbound/outbound distinction, and network-level resource policy.
- `packages/bitcoin-knots/src/net_processing.cpp` covers peer message processing, protocol behavior, misbehavior responses, and relay-adjacent boundaries.
- `packages/bitcoin-knots/src/net_permissions.cpp` covers permission flags such as `noban`, `download`, `addr`, `relay`, `forcerelay`, `mempool`, and `forceinbound`.
- `packages/bitcoin-knots/src/addrman.cpp` covers address storage, freshness, routability, `GetAddr`, tried/new buckets, and source-aware behavior.
- `packages/bitcoin-knots/src/banman.cpp` covers ban, discourage, expiry, unban, and persistence behavior.

## Planning Implications

- Build from the existing pure peer model first; avoid placing listener, socket, clock, filesystem, or runtime effects into pure network crates.
- Add daemon/listener effects in shell-owned runtime code, probably near `open-bitcoin-node`/`open-bitcoin-rpc` boundaries, while keeping reusable admission, permission, eviction, and resource rules testable as pure contracts.
- Keep permission parsing and effect modeling narrower than Knots initially: v1.9 can parse or reject relay-adjacent permission names, but must not enable transaction relay, compact blocks, or mempool propagation.
- Treat address work as a boundary milestone: local address advertisement, bounded `getaddr` response behavior, and a typed address-management contract are useful without claiming full address relay parity.
- Make eviction, ban, discourage, and DoS/resource behavior visible through status, metrics, logs, support bundles, and deterministic tests before any public-network listener UAT.
- Preserve default verification determinism. Public-network listener exposure should stay opt-in UAT; default `bash scripts/verify.sh` should use pure, synthetic, or loopback-safe tests.

## Recommended Phase Order

1. Inbound listener and admission policy.
2. Peer permissions and connection classes.
3. Address advertisement and discovery boundaries.
4. Eviction, ban, and misbehavior policy.
5. DoS and resource governance.
6. Network participation evidence and release boundary.

## Deferred

- Transaction relay and mempool propagation.
- Compact block relay.
- Full address-relay network participation.
- Public inbound serving by default.
- Production full-node readiness claim.
- Production service packaging or public-network CI.
