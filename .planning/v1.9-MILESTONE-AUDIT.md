## Integration Findings

### INT-01: Peer-policy runtime bridge gap

Affected requirements: EVICT-03, EVICT-04, DOS-03, DOS-04.

Phase 93 built pure ban, unban, and misbehavior policy behavior and Phase 93 verification passed. The integration checker found that live managed runtime projection does not carry those policy decisions through: `ManagedPeerNetwork::peer_policy_info()` counts eviction candidates and passes `Some(self.peer_manager.eviction_decision())`, but passes empty misbehavior, ban, and unban slices to `ManagedPeerPolicyInfo::from_policy_decisions`.

Evidence:

- `packages/open-bitcoin-node/src/network.rs:127`
- `packages/open-bitcoin-node/src/network.rs:207`
- `packages/open-bitcoin-node/src/network/inbound.rs:94`
- `packages/open-bitcoin-rpc/src/context/network.rs:211`
- `packages/open-bitcoin-network/src/peer.rs:239`

Broken flow: durable ban/misbehavior policy -> runtime peer-policy status/reconnect suppression.

### INT-02: Inbound metric sample production gap

Affected requirements: INB-05, DOS-04.

Inbound metric kinds and CLI dashboard labels exist, but the static integration check found no producer appending inbound `MetricSample` values. Current persisted metric sample generation appears to come from sync summaries only, which means inbound admission and resource-governance outcomes may be visible in status but do not flow into retained metric history for dashboard consumers.

Evidence:

- `packages/open-bitcoin-node/src/metrics.rs:24`
- `packages/open-bitcoin-node/src/metrics.rs:231`
- `packages/open-bitcoin-node/src/sync/types/summary.rs:248`
- `packages/open-bitcoin-node/src/sync/runtime_state.rs:99`
- `packages/open-bitcoin-cli/src/operator/dashboard/model.rs:506`

Broken flow: inbound counters -> persisted metric samples -> dashboard history.

### INT-03: Phase 90 requirements status gap

Affected requirements: INB-01, INB-02, INB-03, INB-04, INB-05, BOUND-06.

Phase 90 verification and summary metadata prove the five INB requirements passed. `.planning/REQUIREMENTS.md` still leaves the same five requirements unchecked and marks their traceability rows `Pending`. This does not create an implementation gap, but it violates the release-boundary traceability requirement that requirements, roadmap, summaries, verification, and audit artifacts map every v1.9 requirement exactly once and consistently.

Evidence:

- `.planning/REQUIREMENTS.md:12`
- `.planning/REQUIREMENTS.md:93`
- `.planning/ROADMAP.md:22`
- `.planning/phases/90-inbound-listener-and-admission-policy/90-VERIFICATION.md:21`

Broken flow: phase completion -> requirements traceability artifact.
