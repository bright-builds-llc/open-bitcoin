## Phase 152: Post-Prune Wallet Rescan Eligibility

**Goal:** Node and durable RPC wallet rescans admit entries only when their creating payloads are present, including midrange scans and chunk resume after actual pruning; leftover snapshots remain non-authoritative.

**Requirements:** SNAP-01. **Gap closure:** INT-02 and the real-prune → midrange-rescan flow. **Depends on:** Phase 151 and the delivered paired unlink from Phase 148. **Directory:** `.planning/phases/152-post-prune-wallet-rescan-eligibility/`.

Four planning tasks:

1. Define one consistent eligibility contract for full wallet replacement versus chunk/range checks, grounded in Phase 146 D-04 and D-08; keep payload I/O in the shell and wallet decisions pure.
2. Enforce that contract on both node chunk/resume and durable RPC range paths. A failed eligibility check must preserve the prior wallet state and never fall back to leftover snapshot bytes.
3. Add regression coverage using real paired Fjall pruning: a live wallet coin created in a deleted height followed by a scan starting above it, chunk resume, missing payload in the requested range, and a valid retained-payload control. Cover both adapters, durable failure evidence, and same-datadir reopen.
4. Record lifecycle-valid SNAP-01 closure evidence, parity breadcrumbs for changed Rust paths, and the relevant documentation. Run the repo-native verifier before marking the requirement complete.

Success criteria:

- Both scan paths enforce eligibility for every entry admitted to a full replacement, including creating heights before the requested start.
- A post-prune midrange scan cannot silently replace the wallet with entries whose creating payload is absent.
- Chunking/resume and same-datadir reopen preserve the same rule and reject leftover snapshot authority.
- Focused runtime regressions and the default verifier pass; source-string presence assertions alone do not prove this flow.

## Phase 153: Automatic Prune Retention Integration

**Goal:** A configured automatic target drives retention in the running durable lifecycle through the existing pure planner and paired-unlink owner, with keep-window, prune-after, locks, recovery, and cache consistency preserved.

**Requirements:** PRUN-01, PRUN-02. **Gap closure:** INT-01 and the automatic-target → ongoing-retention flow. **Depends on:** Phase 152, plus the delivered policy, unlink, serving, and operator surfaces from Phases 147–150. **Directory:** `.planning/phases/153-automatic-prune-retention-integration/`.

Four planning tasks:

1. Obtain authoritative retained block/undo usage, per-height sizes, chain-parameter prune-after height, resolved mode, tip, and current durable locks in the shell. Define the Fjall byte-accounting boundary without adding a second block store or new production dependencies.
2. Invoke `plan_automatic_prune` from the production retention/flush lifecycle and apply its candidates through the existing durable owner. Disabled/manual-only modes must not perform automatic deletion; keep callback-driven undo forgetting and block-cache eviction on success and error.
3. Test the production lifecycle through real storage with an exceeded target: paired delete and have-pruned, no deletion below the target or prune-after threshold, 288-block retention, durable lock buffer, later-flush error/cache eviction, and reopen finish-or-refuse. Include a configured-mode control that would catch a return to an empty automatic plan.
4. Update product/parity evidence and requirement completion only after lifecycle-valid verification. Confirm operator quartet, honest labels, support redaction, and the Phase 152 wallet contract still hold; rerun the milestone audit after this phase.

Success criteria:

- An automatic target of at least 550 MiB has a production planner caller using measured retained payload facts.
- Ordinary lifecycle activity can durably delete eligible paired payloads when usage exceeds the target, without requiring a manual RPC call.
- Recent heights, prune-after gating, named lock buffers, and disabled/manual-only behavior remain protected.
- Real-delete status, cache/undo consistency, and restart behavior remain correct, and full verification passes.
